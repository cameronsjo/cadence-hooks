# cadence-hooks

Rust workspace (8 crates) compiling to a single `cadence-hooks` binary. Dispatches Claude Code hook checks via clap subcommands, organized by namespace (cadence, guardrails, rules, obsidian, metrics, session).

## Build & Test

- `make ci` = fmt-check + clippy `-D warnings` + all tests. Run before every commit.
- cargo lives at `~/.cargo/bin` — `export PATH="$HOME/.cargo/bin:$PATH"` before `make` or `cargo` (the pre-commit hook adds it itself).
- `cargo fmt --all` before `make ci` after writing long assert lines — fmt-check fails CI otherwise.
- **Local `make ci` green does NOT guarantee CI green — and toolchain drift is the SECOND cause to check, not the first.** Until 2026-09-06 the `clippy` target ran `cargo clippy --workspace` with no `--all-targets`, so it never linted test code at all while CI did: a lint in a `#[cfg(test)]` module passed locally and failed CI with matching toolchains on both sides. That misreads as toolchain drift every time, and the `rustup update` it prescribes fixes nothing. The target now carries `--all-targets` (cadence-hooks#874). **Before blaming the toolchain, compare the two invocations and confirm `cargo clippy --version` actually differs from CI's** — the real drift case is real (CI runs latest stable, which flags lints an older local clippy doesn't, e.g. `collapsible_match` on 1.96), so `rustup update` before a PR is still worth it, but only after the flags match.

## Specs and changes (OpenSpec)

cadence-hooks plans work with [OpenSpec](https://github.com/Fission-AI/OpenSpec) (#1446).

- `openspec/specs/<capability>/spec.md` says what the shipped binary does: each hook's verdicts, messages, switches and files. Read the relevant spec before changing a hook.
- New behavior starts as a change: `openspec/changes/<id>/` with `proposal.md`, delta specs, `design.md` when it needs one, and `tasks.md`. `/opsx:propose`, `/opsx:apply` and `/opsx:archive` drive it in Claude Code (the `openspec-*` skills in Codex). Every change links its issue.
- Archive a change (`scripts/openspec.sh archive <id>`) in the PR that finishes it, so the specs move with the code.
- Run the CLI only through `scripts/openspec.sh`, which installs the pinned version from `scripts/openspec/package-lock.json` (needs Node 20.19+ or 22.13+). CI runs `scripts/openspec.sh validate --all --strict --no-interactive`.
- The `openspec-*` skills and `/opsx` commands are generated. After `scripts/openspec.sh update`, run `scripts/openspec-localize.sh`: it points them at the pinned wrapper and pre-allows only the read and validate subcommands they run, so `init`, `update` and `archive` still ask. CI and `tests/openspec_skills.rs` fail until you do. The wrapper refuses `feedback`, `completion`, `config`, `workset`, `store`, `--store` and `context --code-workspace` (they reach outside the repo) unless `OPENSPEC_ALLOW_OUTSIDE=1`.
- `docs/plans/` is frozen: `tests/plans_freeze.rs` rejects a plan dated after 2026-10-20. The plans already there finish in place. `.claude/settings.json` points `CADENCE_PLANS_DIR` at the gitignored `.claude/plans/`, so `persist-plan-approval` keeps saving approved plans without tripping the freeze.
- ADRs in `docs/adr/` stay. A spec says what the behavior is; an ADR says why. `docs/hooks.md` stays the operator catalog.

## Release (fully automated — do NOT create tags or edit the tap formula manually)

1. Every PR stages its CHANGELOG bullet under `## [Unreleased]`. On each push to main, `prepare-release.yml` keeps one `chore(main): release X.Y.Z` PR current (branch `prepare-release/main`): `scripts/prepare-release.sh` picks the version (`### Fixed` only → patch, anything else → minor), runs `make bump`, moves the workspace lines in `Cargo.lock`, and adds a `## [X.Y.Z] - DATE` heading under `## [Unreleased]`. The App commits it through the REST API so GitHub signs it. An empty `[Unreleased]` closes the PR.
2. `ship.yml` (nightly, cadence-ecosystem ADR-0044) merges that PR when `.github/scripts/ship-gate.sh` verifies it. Ship now with `gh workflow run ship.yml -R cameronsjo/cadence-hooks`; the gate still applies. Never edit the vendored gate; re-copy it from cadence-ecosystem `scripts/release/`.
3. `auto-tag.yml` creates the `vX.Y.Z` tag, but only for the App's own merge of its release PR (a hand-merged or feature-PR version bump fails the run and is not tagged) → `release.yml` refuses the tag unless its commit is on main with a green `CI` push run, then builds the platform binaries, publishes the GitHub Release, and a separate `homebrew` job sends the `repository_dispatch` that updates `cameronsjo/homebrew-tap`'s formula. A red `CI` on main therefore blocks releases until it is fixed.

Do not hand-bump or push to `prepare-release/main`: the gate refuses commits the App did not make, and the next push to main rebuilds the branch anyway.

Manual tagging or formula edits race the automation. Post-release: `brew update && brew upgrade cadence-hooks`, verify `cadence-hooks --version`.

**Two upkeep steps for the `cadence` plugin's `platform-drift` check** (`plugins/cadence/config/platform-baseline.json` in the cadence monorepo — the SessionStart nudge and `doctor`'s unconditional status report both read it):

1. **Every cadence-hooks release bumps `cadence_hooks.current_version` to the new tag.** Derive it from the tag (`gh release view -R cameronsjo/cadence-hooks --json tagName`), never hand-type it — parallel sessions release from this repo too. Read the current value first (`gh api repos/cameronsjo/cadence/contents/plugins/cadence/config/platform-baseline.json`) and skip the bump if it already names your tag. The edit lands in a `cameronsjo/cadence` checkout through a PR there; a direct push to that repo's main is rejected. A CI backstop is **live** (cameronsjo/cadence#1369, merged 2026-09-20): a scheduled job compares the recorded value against this repo's latest release within a day and files one deduplicated issue **on `cameronsjo/cadence`**. It never replaces this step: it notices a miss after the fact, and the value was six releases stale before a human caught it last time. It files an issue rather than opening the bump PR because *Allow GitHub Actions to create and approve pull requests* is off on `cameronsjo/cadence`, so `GITHUB_TOKEN` is refused at `gh pr create` — a deliberate choice, since flipping that setting would widen every workflow in that repo to save one click here.
2. **Every future platform-adoption sweep bumps `claude_code.last_swept_version`** to the Claude Code version swept, alongside `swept_on`.

A stale baseline in either direction fails open (ADR-0001) — it never blocks, just under- or (if hand-typed wrong) over-nudges.

**Each PR stages its CHANGELOG bullet under `[Unreleased]`; at release time, attribute bullets by tag, not convenience.** Staging under `[Unreleased]` per PR *is* the intended workflow — every recent fix PR adds its bullet there, and the release PR only adds a `## [X.Y.Z] - DATE` heading above those bullets, keeping `## [Unreleased]` (the older hand flow renamed it instead). This rule governs release-time *sectioning*, not whether to hand-maintain the changelog. The drift to avoid: back-to-back releases (0.15–0.19) left already-shipped bullets sitting under `[Unreleased]`. At release time, place each bullet under the version that actually shipped it — find it with `git tag --contains <commit>` — rather than folding everything into the new version. `release.yml` uses `generate_release_notes: true`, so the *public* release notes come from PRs since the last tag while the hand-maintained CHANGELOG is a *separate* artifact — the two coexist by design; a mis-sectioned changelog silently contradicts the published release notes (and `make bump` only touches Cargo.toml, so the CHANGELOG is a separate, hand-maintained edit).

**A new CHANGELOG bullet must sit under `## [Unreleased]`, and CI checks it.** The `CHANGELOG sections` job runs `scripts/check-changelog-sections.sh`, which fails a PR whose new top-level bullet sits under a version heading. To list every bullet added since a tag by hand: `git diff <last-tag> origin/main -- CHANGELOG.md | grep -E '^\+- '`.

**Held-version bundling still hits a real `CHANGELOG.md` merge conflict, not a clean fast-forward, when two PRs both stage a bullet under `[Unreleased]`.** Merging the first PR lands cleanly; the second PR's branch then reports `GraphQL: Pull Request has merge conflicts` on the exact same file both PRs were told to touch (per "Each PR stages its CHANGELOG bullet under `[Unreleased]`" above). Fix: `git merge origin/main` into the second PR's branch, keep both bullets (they're additive, not competing), push, then merge. Held-version bundling prevents double-*releases*; it doesn't prevent this one predictable merge conflict. (Bit bundling #391/#393 into 0.67.0, 2026-07-24.)

**A release stamp on `main` mis-sections an open branch's `[Unreleased]` bullet, and the merge is clean, not a conflict**: the bullet lands under the new `## [X.Y.Z]`, a release that does not contain it. The `CHANGELOG sections` job fails the PR on its next push (a merge-up counts); move the bullet back under `## [Unreleased]`. CI does not re-run when main moves, so a stamp after the last push shows up only at the next one.

## Gotchas

- **Write every hooks.json `if:` as a single rule — pipe alternation is a silent PostToolUse dead end.** The platform docs specify one rule per `if:` with no alternation; live behavior is worse than a flat "unsupported", because it *works on PreToolUse* and **silently never matches on PostToolUse**. Nothing errors — the hook simply never fires, so a fully-tested subcommand ships and does nothing. `log-polish-nudge` was dead from 2026-06-27 to 2026-07-25 for exactly this reason, across 129+ matching ship anchors, and was only caught when someone noticed its ledger had never been created (proven on 2.1.220, cameronsjo/cadence#593). The PreToolUse half working is the trap: it makes alternation look supported and licenses the pattern into a PostToolUse entry where it dies. The estate's hooks.json files are normalized to single-rule form with a CI reintroduction guard in the plugin monorepo (cameronsjo/cadence#596) — do not reintroduce alternation to pass that guard, split the entry instead. For checks that must fire on pipelines (e.g. `warn-alias-parsing`), note that an `if:` glob still cannot match a literal `|`: enumerate tool names in the filter and let the binary's pipe check do the precision work.
- **`if:` sits on the HOOK object, not the entry that wraps it** — `hooks[<event>][i].hooks[j].if`, one level deeper than `matcher`. A parse reading `entry.get("if")` returns `None` for every hook and prints a confident "no filter", which reads as "this hook fires on everything" when it is gated to two commands. Verify a filter by reading the raw JSON around the command string, not by a structural query you wrote from memory. **A hook wired with no matching `if:` is inert** — the binary never spawns, so a fully-tested subcommand can ship and do nothing; that is the wiring half of the two-PR shape, and the binary repo's CI cannot see it. (Both bit the #325 merge-anchor wiring, 2026-07-26.)
- **Registry/dispatch invariant**: every hook subcommand needs both a clap variant (src/main.rs) and a `HOOKS` entry (src/registry.rs) — including an `event` field that matches the `HookEvent` passed in the dispatch (`None` for loggers). The `registry_matches_clap_dispatch` unit test enforces this on every `cargo test`; the hooks.json audit test (`tests/hook_registration_audit.rs`) additionally cross-checks the plugin wiring. **Every wiring assertion runs against two subjects: the checked-in manifest fixture (`tests/fixtures/registration-audit/`, always) and the sibling `cadence` monorepo checkout (when one is present locally).** The fixture is what puts the audit on CI's gating leg — CI has no sibling checkout, so before the fixture landed every wiring assertion returned early there and 20 tests reported `ok` having asserted nothing. A red assertion names its subject in brackets (`[checked-in fixture]` or `[sibling cadence checkout]`), which is the first thing to read. Both subjects resolve `cadence/plugins/<name>/hooks/hooks.json` (monorepo-first, with the retired standalone path as fallback). **The sibling leg fails *locally* when that checkout lacks not-yet-merged wiring — including when it is merely a few commits behind `origin/main`.** It reads the sibling's *working tree*, so before treating a `[sibling cadence checkout]` failure as drift, run `git -C <workspace-root>/cadence status -sb`: a `behind N` checkout produces confident false findings. Only chase such a failure if `registry_matches_clap_dispatch` *also* fails (that's a real internal bug). A `[checked-in fixture]` failure is never checkout staleness and must always be chased. `fixture_manifests_match_the_monorepo_default_branch` keeps the fixture honest by comparing it to the sibling's **`origin/main`** — not its working tree, precisely so a parked or behind checkout cannot manufacture fixture drift; `git -C <workspace-root>/cadence fetch origin` first, since that ref is only as current as the last fetch. **That triage covers the wiring assertions only — a `refusing to audit a partial scan` failure is never checkout staleness and must always be chased**: it means a `BINARY_PLUGIN_DIRS` entry names a plugin directory that does not exist, and until it is fixed every assertion in the file is dead. The *sibling* leg skips **only when nothing resolves AND the checkout is confirmed absent** — bare CI, where there is no second subject. Anything else fails: a partial resolve, or nothing resolving while the checkout *is* present (which means every path the audit knows is stale). The fixture leg has no skip branch at all. It used to skip on any unresolved manifest, which is how a single retired-plugin entry (`cadence-canon`) turned the whole file into a false green: 20 tests reported `ok` with no assertion body ever running. `CADENCE_AUDIT_WORKSPACE_ROOT` overrides the sibling search root, which is how you verify against a fixture without touching a checkout another session is using — it must point at a real directory, or the audit fails rather than silently resolving nothing.
- **Hook subcommands are stdin-driven** — run bare in a terminal they print guidance and exit 1 (never hang, never block). `cadence-hooks try <ns> <sub>` is the manual-test path: it runs any hook against `--payload <FILE>`, else a payload piped to stdin, else a generated sample, and reports the outcome (`--show-payload` echoes the payload in full).
- **A guard probe must name which guard owns the payload's shape before reading its verdict — a single-guard probe manufactures false bypasses.** Guards partition by shape, not by danger: `cadence prevent-secret-leaks` owns reads and `cadence prevent-secret-writes` owns writes, so a redirect like `echo $'a\'b' > .env` reads `ALLOW` under the leaks guard and `BLOCK` under the writes guard. Piping a whole attack corpus at one subcommand therefore reports a live bypass for every row whose shape that guard was never responsible for — confidently, with a clean exit and nothing in stderr to say the probe asked the wrong question. Route each string to the guard that owns its shape, or run the corpus across every guard and read the verdicts as a set. (Surfaced verifying cadence-ecosystem#479 during the #652 work, 2026-09-04; `scripts/consumer-differential.sh` is the corpus-across-every-subcommand form.)
- **`try` also overrides the sample payload's `cwd` with the *process* cwd** — so a `registry::sample_for` override that sets `cwd:"/tmp"` is silently ignored; `try` injects the directory you run it from. A check that resolves git state from `input.cwd` therefore tests the **live checkout you're standing in**, not the hermetic sample dir — `try guardrails warn-subagent-worktree` from the cadence-hooks checkout *nudged* (its `/tmp` sample notwithstanding) because the cwd became the real repo, which has a sibling worktree. Useful (real-state smoke test) but not hermetic: `--show-payload` echoes the substituted cwd, and for an isolated case pipe a crafted payload to the bare `cadence-hooks <ns> <sub>` (which honors the payload `cwd`) instead of `try`. (2026-06-22.)
- **TTY-dependent behavior (the interactive-terminal guard) cannot be tested via Claude's Bash tool** — it pipes stdin, so `is_terminal()` is always false there. Verify with `script -q /dev/null cadence-hooks <ns> <sub>` (allocates a pty) or a real terminal.
- **`rules validate-frontmatter` no-ops on paths without a `skills/<dir>/` ancestor.** Manual-testing the skill-`name:` check needs a real `.../skills/<dir>/SKILL.md` path in the Write payload — a bare `mktemp` path makes the check skip entirely and return a **false PASS for every name**, even a deliberately-wrong suffix. Build the payload with `jq` against a `skills/<dir>/` path, and include a wrong-suffix case as a control: it must exit 2 to prove the validator actually engaged (otherwise an all-PASS run is meaningless).
- **Guards fail open (ADR-0001)**: parse failures, unreadable files, and unknown subcommands exit 0/1, never 2. A guard's own failure must never block the user.
- **CADENCE_BYPASS=1 exempts the CLI actions (`list`, `manifest`, `configure`, `doctor`, `try`, `migrate-config`, `session declare|status|plans|timer`, `metrics grade|price`) and `guardrails enforcement-status`** — diagnostic/CLI commands must work during maintenance; enforcement hooks are bypassed.
- **Repro scripts/fixtures containing flagged terminology must build the term by concatenation** (`TERM_W="$(printf 'white%s' 'list')"`) — the installed terminology guard blocks Writes containing the literal to any non-excluded path, including `/tmp`. CLAUDE.md and `cadence-hooks/` paths are excluded; scratch fixtures elsewhere are not.
- **A commit message or PR body that names a secret file blocks in one shape only:** when the same Bash command sets positional parameters (`prevent-secret-leaks`, cameronsjo/cadence-hooks#1443). Run the `git commit` or `gh` command that carries the message or body in its own Bash call. Quoting a force push, a `> .env` redirect or a secret filename in `-m`, a heredoc or `--body` passes every Bash guard (re-probed on 0.130.0).
- **Guards stop accidents, not adversaries (cadence-ecosystem ADR-0046, #1442).** The threat model is a cooperative model making plausible mistakes, so five rules govern every guard change:
  1. A spelling only a deliberate attacker would type (brace padding, NBSP and other non-bash blanks, `eval` floods, function or positional-parameter indirection, `pus{h..h}`, `A[0]=x git push`) is out of scope: no fix, no issue, and such an issue closes as not planned.
  2. A guard blocks only when it read the command exactly (no guessing at variables, `cd`s or aliases) and the harm is costly to undo: a secret leaving the machine or entering the context, a force-push to main, local work destroyed (`reset --hard`, `clean -f`, vault deletions), a repo deleted, a write to a repo the operator does not own, a commit into a shared primary checkout, unscrubbed text promoted into the off-machine runbooks folder. A new kind needs a line in ADR-0046. Everything else nudges or goes.
  3. When the parser cannot resolve a shape, the guard judges what it did read and allows the rest. A nudge is allowed only when it names a concrete action. No guard refuses a command for being hard to read.
  4. A review of guard code scores the everyday-command corpus (a few hundred routine commands for the touched guard) at head against `origin/main` **first**; any new ALLOW→BLOCK fails the review unless the operator accepted it. A reviewer hunts misses only inside rule 1's threat model and files no "remaining gaps" issue for an out-of-scope miss. Brief `cadence-forge:security-reviewer` with these rules, not with "find inputs where a dangerous command slips through unseen" — that framing is what built the 2026-09/10 false-positive ratchet (#1434, #1435, #1441, #1437 and dozens before them).
  5. A blocking guard that draws two false-block feedback issues in 30 days drops to a nudge, or loses the leg that misfires, until it is redesigned (the feedback issues are the trigger; a `denials.jsonl` count is supporting evidence, and narrowing to rule 2's literal cases counts as the redesign); never patch it spelling by spelling (#1303 is the redesign shape: literal names handed to an enumerated reader).

  Parser invariants still hold where they protect a block the guard is certain about: drop content only when a boundary is confidently located, and when a predicate that drove only a nudge starts driving a state mutation, review that transition (0.30.0's #70 re-anchoring).
- **Security-review and code-review each catch Criticals the other misses on guard code — run both, not either alone.** On the #775 marker-attestation chain, an Opus `cadence-forge:security-reviewer` caught a prompt-injection channel (a marker-recorded value reaching hook `additionalContext` unvalidated — the read side never re-applied the record-side charset the comment claimed) that a quality lens would not frame as a bug; a separate Opus `cadence:code-reviewer` then caught a correctness Critical the security pass missed — `working_tree_digest` hashed path *names* only when run from a subdirectory (two git subprocesses returning paths in different spaces), content-blind to the very thing it attests. Neither pass is a superset of the other: security hunts the trust boundary, review hunts the logic. A security-touching guard change earns both, and verify each finding's fix live before trusting it. (2026-08-26.)
- **The `markdown-lint` hook allows without a word when no `markdownlint` CLI is on `PATH`**; `cadence-hooks doctor` prints a note naming the install command. The repo ships no markdownlint config, so defaults flag MD013 (line-length) / MD060 (table-padding) noise the existing docs already violate — filter to *structural* findings.
- **Scope env-var verification greps to shipped source.** A loose `grep -rn "CADENCE_" --include='*.rs'` over-reports the binary's live env surface — it sweeps in `tests/` and stale `.claude/worktrees/` checkouts. Grep `crates/*/src src` to see what the *shipped* binary actually honors. **`CADENCE_METRICS_DIR` is LIVE production**, not test-only — it is the *primary* resolution tier in `metrics_dir()` (`crates/metrics/src/common.rs`, ahead of the `CLAUDE_CONFIG_DIR`/`~/.claude` fallback) and is read in production by every `crates/metrics/src/log_*.rs` writer (e.g. `log_subagent.rs`) and by `crates/session/src/persist_plan.rs`. (A #271 red-team refuted the earlier "test-only/dead" reading of claude-configurations#120 — the shipped-source grep it prescribes was itself misread. The grep discipline stands; that one conclusion was wrong.)
- **RESOLVED by #403:** the Scratch/E2E carve-out false-ALLOW (checkout under `.claude/worktrees/` or `/tmp` made every fixture inherit the carve-out and every verdict read ALLOW) is fixed — `Scratch::new` now auto-relocates via `resolve_scratch_dir` (`crates/core/src/git_fixtures.rs`); see CONTRIBUTING.md § Running the suite from a worktree.
- **`cargo test` does not build the `cadence-hooks` binary** — pipe-probing it without `cargo build --bin cadence-hooks` first exits 127, which misreads as a false ALLOW. (Bit the #226 verification, 2026-07-06.)
- **`git worktree move` leaves stale `CARGO_BIN_EXE_*` paths baked into already-compiled test binaries** — integration tests that exec the binary then fail `No such file or directory` at the *old* worktree path, and cargo sees nothing to rebuild, so the red suite reads as a phantom regression. `cargo clean` after any worktree move. (Bit the #288 merge verification after manually relocating a `/tmp` worktree — the pre-#403 workaround — 2026-07-20.)
- **RESOLVED by #403:** `session start`'s posture-test inversion (same carve-out silenced the posture line, so `posture_line_*`/`run_start_*` tests asserting FIRES failed while an `Allow`-only test passed for the wrong reason) is fixed — `start.rs`'s hand-rolled `Scratch` is migrated onto the shared, relocating one. **A local red/green split across posture tests is a location signal, not a verdict** — still true as general caution for any test reading real process env, see the entry below. (Originally cost 4 undetected findings across a 6-PR arc, 2026-07-26.)
- **Test helpers that lock a process-global env var must be the ONLY helper locking it.** `persist_plan` carried its own private `ENV_LOCK` for `CADENCE_METRICS_DIR` while `registry::test_metrics_env` guarded the same global through a different mutex — two uncoordinated locks are a race no critical section can fix, and it stayed latent until added test volume shifted scheduling (surfacing first on the Windows runner as a `NotFound` unwrap on a metrics read). One global, one lock, one helper; import the existing one rather than minting a sibling. Ruling a failure like this in or out as a *production* bug turns on WHICH assertion failed, not on inspection. (cadence-hooks#446, 2026-07-26.)
- **A Claude session's shell can carry `CADENCE_DISABLE`, `CADENCE_ALLOW_MAIN` or `CADENCE_BYPASS`, and each one exempts guards**, so a block assertion fails or passes for the wrong reason (a disabled guard says so one line lower in stderr: `'enforce-worktree' disabled via CADENCE_DISABLE`). `make test` and `tests/support`'s `cadence_hooks()` clear all three. A hand pipe-probe, a bare `cargo test` (unit tests read process env) or a test that builds its own `Command` does not, so run those under `env -u CADENCE_DISABLE -u CADENCE_ALLOW_MAIN -u CADENCE_BYPASS`. A unit test that needs a fixed value pins it (`with_worktree_env` in `crates/session/src/start.rs`).
