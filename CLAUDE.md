# cadence-hooks

Rust workspace (8 crates) compiling to a single `cadence-hooks` binary. Dispatches Claude Code hook checks via clap subcommands, organized by namespace (cadence, guardrails, rules, obsidian, metrics, session).

## Build & Test

- `make ci` = fmt-check + clippy `-D warnings` + all tests. Run before every commit — the pre-commit hook also needs cargo on PATH.
- cargo lives at `~/.cargo/bin` — `export PATH="$HOME/.cargo/bin:$PATH"` in every shell invocation, including git commits (the pre-commit hook runs cargo and aborts silently without it).
- `cargo fmt --all` before `make ci` after writing long assert lines — fmt-check fails CI otherwise.
- **Local `make ci` green does NOT guarantee CI green when the local Rust toolchain trails CI's.** CI runs the latest stable clippy, which flags lints the older local clippy doesn't (e.g. `collapsible_match` on 1.96). Treat the first CI run as the real clippy verdict, or `rustup update` before a PR.

## Release (fully automated — do NOT create tags or edit the tap formula manually)

1. `make bump VERSION=X.Y.Z` (updates Cargo.toml), then `cargo check` to refresh Cargo.lock
2. Commit both files, push to main
3. `auto-tag.yml` creates the `vX.Y.Z` tag → `release.yml` builds 4 platform binaries, publishes the GitHub Release, and sends a `repository_dispatch` that updates `cameronsjo/homebrew-tap`'s formula

Manual tagging or formula edits race the automation. Post-release: `brew update && brew upgrade cadence-hooks`, verify `cadence-hooks --version`.

**Two upkeep steps for the `cadence` plugin's `platform-drift` check** (`plugins/cadence/config/platform-baseline.json` in the cadence monorepo — the SessionStart nudge and `doctor`'s unconditional status report both read it):

1. **Every cadence-hooks release bumps `cadence_hooks.current_version` to the new tag.** Derive it from the tag (`gh release view -R cameronsjo/cadence-hooks --json tagName`), never hand-type it — parallel sessions release from this repo too, and a stale value under-nudges (degrades quietly: no error, just a check that never fires). A CI automation for this bump is a named follow-up, not yet built.
2. **Every future platform-adoption sweep bumps `claude_code.last_swept_version`** to the Claude Code version swept, alongside `swept_on`.

A stale baseline in either direction fails open (ADR-0001) — it never blocks, just under- or (if hand-typed wrong) over-nudges.

**From a Claude session the bump commit to main is blocked by this repo's own `enforce-worktree` guard** (a primary-checkout `git commit`), unless the session happens to carry `CADENCE_ALLOW_MAIN` in its env. Do the bump in a worktree and push its tip to main: `git worktree add .claude/worktrees/release-X -b release/X origin/main`, then `make bump` + `cargo check` + stamp the CHANGELOG (`## [Unreleased]` → `## [X] - DATE`) **in the worktree**, `git commit`, then `git push origin release/X:main` (fast-forward → triggers auto-tag). `git rebase` is also guard-blocked (git-safety hook), so reshape commits with `reset`, not rebase. Note `release.yml` builds and publishes even when `ci.yml` is red (it doesn't gate on the test suite) — verify the release via the tag/Release workflow/tap formula, not the CI check.

**Check `git log --oneline -5` on main for bump commits before choosing the next version number.** Parallel Claude sessions release from this repo too — a 0.15.1 shipped mid-session while another session was building what became 0.15.2. The race only surfaced because the bump commit failed loudly; don't rely on that.

**Each PR stages its CHANGELOG bullet under `[Unreleased]`; at release time, attribute bullets by tag, not convenience.** Staging under `[Unreleased]` per PR *is* the intended workflow — every recent fix PR adds its bullet there, and the release commit only stamps the date onto those bullets (`## [Unreleased]` → `## [X.Y.Z] - DATE`). This rule governs release-time *sectioning*, not whether to hand-maintain the changelog. The drift to avoid: back-to-back releases (0.15–0.19) left already-shipped bullets sitting under `[Unreleased]`. At release time, place each bullet under the version that actually shipped it — find it with `git tag --contains <commit>` — rather than folding everything into the new version. `release.yml` uses `generate_release_notes: true`, so the *public* release notes come from PRs since the last tag while the hand-maintained CHANGELOG is a *separate* artifact — the two coexist by design; a mis-sectioned changelog silently contradicts the published release notes (and `make bump` only touches Cargo.toml, so the CHANGELOG is a separate, hand-maintained edit).

**To bundle N PRs into ONE release, hold the version.** Every push to `main` that changes the `Cargo.toml` version auto-tags and releases — so merging N version-bumping PRs cuts N releases. When landing a merge train, resolve each rebased PR's `Cargo.toml`/`Cargo.lock` version conflict to `main`'s *current* value (`git checkout --ours Cargo.toml Cargo.lock`, then `cargo build` to re-sync the lock) so the merges don't auto-tag, then `make bump` **once** at the end for a single release. (Verified 2026-06-08 bundling #75/#76/#78 into 0.25.0; #79 had already self-released 0.24.0 on its own merge because its bump survived.)

**Held-version bundling still hits a real `CHANGELOG.md` merge conflict, not a clean fast-forward, when two PRs both stage a bullet under `[Unreleased]`.** Merging the first PR lands cleanly; the second PR's branch then reports `GraphQL: Pull Request has merge conflicts` on the exact same file both PRs were told to touch (per "Each PR stages its CHANGELOG bullet under `[Unreleased]`" above). Fix: `git merge origin/main` into the second PR's branch, keep both bullets (they're additive, not competing), push, then merge. Held-version bundling prevents double-*releases*; it doesn't prevent this one predictable merge conflict. (Bit bundling #391/#393 into 0.67.0, 2026-07-24.)

## Gotchas

- **Ignore `make bump`'s "next steps" output** — it suggests `git tag` + `git push --tags`, which predates and races the auto-tag automation. Just commit and push; `auto-tag.yml` owns tagging.
- **Write every hooks.json `if:` as a single rule — pipe alternation is a silent PostToolUse dead end.** The platform docs specify one rule per `if:` with no alternation; live behavior is worse than a flat "unsupported", because it *works on PreToolUse* and **silently never matches on PostToolUse**. Nothing errors — the hook simply never fires, so a fully-tested subcommand ships and does nothing. `log-polish-nudge` was dead from 2026-06-27 to 2026-07-25 for exactly this reason, across 129+ matching ship anchors, and was only caught when someone noticed its ledger had never been created (proven on 2.1.220, cameronsjo/cadence#593). The PreToolUse half working is the trap: it makes alternation look supported and licenses the pattern into a PostToolUse entry where it dies. The estate's hooks.json files are normalized to single-rule form with a CI reintroduction guard in the plugin monorepo (cameronsjo/cadence#596) — do not reintroduce alternation to pass that guard, split the entry instead. For checks that must fire on pipelines (e.g. `warn-alias-parsing`), note that an `if:` glob still cannot match a literal `|`: enumerate tool names in the filter and let the binary's pipe check do the precision work.
- **`if:` sits on the HOOK object, not the entry that wraps it** — `hooks[<event>][i].hooks[j].if`, one level deeper than `matcher`. A parse reading `entry.get("if")` returns `None` for every hook and prints a confident "no filter", which reads as "this hook fires on everything" when it is gated to two commands. Verify a filter by reading the raw JSON around the command string, not by a structural query you wrote from memory. **A hook wired with no matching `if:` is inert** — the binary never spawns, so a fully-tested subcommand can ship and do nothing; that is the wiring half of the two-PR shape, and the binary repo's CI cannot see it. (Both bit the #325 merge-anchor wiring, 2026-07-26.)
- **The git-safety hook (this repo's own product) blocks `git rebase` in Claude sessions.** To rebase a stacked PR branch onto main: cherry-pick its own commits onto a fresh branch from main, then `git push origin <tmp-branch>:<pr-branch> --force-with-lease`.
- **Registry/dispatch invariant**: every hook subcommand needs both a clap variant (src/main.rs) and a `HOOKS` entry (src/registry.rs) — including an `event` field that matches the `HookEvent` passed in the dispatch (`None` for loggers). The `registry_matches_clap_dispatch` unit test enforces this on every `cargo test`; the hooks.json audit test (`tests/hook_registration_audit.rs`) additionally cross-checks the sibling `cadence` monorepo checkout when it's present locally, resolving `cadence/plugins/<name>/hooks/hooks.json` (monorepo-first, with the retired standalone path as fallback). **That cross-sibling check (`all_binary_subcommands_are_registered`) fails *locally* when the sibling checkout lacks not-yet-merged wiring — including when it is merely a few commits behind `origin/main` — but GitHub CI has no siblings and skips it, so the GitHub Check legs, not local `make ci`, gate a merge.** The audit reads the sibling's *working tree*, so before treating a failure as drift, run `git -C <workspace-root>/cadence status -sb`: a `behind N` checkout produces confident false findings. Only chase a local audit failure if `registry_matches_clap_dispatch` *also* fails (that's a real internal bug). The audit skips **all-or-none** — a partial resolve (one leftover pre-consolidation checkout) is a broken environment, not a finding, and the skip message lists every path it tried. `CADENCE_AUDIT_WORKSPACE_ROOT` overrides the sibling search root, which is how you verify against a fixture without touching a checkout another session is using.
- **Hook subcommands are stdin-driven** — run bare in a terminal they print guidance and exit 1 (never hang, never block). `cadence-hooks try <ns> <sub>` is the manual-test path: it runs any hook against a generated sample payload and reports the outcome. **`try` IGNORES stdin** — it always runs a *generated* sample unless you pass `--payload <FILE>` (add `--show-payload` to confirm it echoed YOUR payload). Piping an attack to `… | cadence-hooks try …` silently tests the canned sample and can falsely show ALLOW; feed real payloads via `--payload`, or pipe straight to the bare `cadence-hooks <ns> <sub>` (no `try`, which *does* read stdin). (Bit hook verification 2026-06-16.)
- **`try` also overrides the sample payload's `cwd` with the *process* cwd** — so a `registry::sample_for` override that sets `cwd:"/tmp"` is silently ignored; `try` injects the directory you run it from. A check that resolves git state from `input.cwd` therefore tests the **live checkout you're standing in**, not the hermetic sample dir — `try guardrails warn-subagent-worktree` from the cadence-hooks checkout *nudged* (its `/tmp` sample notwithstanding) because the cwd became the real repo, which has a sibling worktree. Useful (real-state smoke test) but not hermetic: `--show-payload` echoes the substituted cwd, and for an isolated case pipe a crafted payload to the bare `cadence-hooks <ns> <sub>` (which honors the payload `cwd`) instead of `try`. (2026-06-22.)
- **TTY-dependent behavior (the interactive-terminal guard) cannot be tested via Claude's Bash tool** — it pipes stdin, so `is_terminal()` is always false there. Verify with `script -q /dev/null cadence-hooks <ns> <sub>` (allocates a pty) or a real terminal.
- **`rules validate-frontmatter` no-ops on paths without a `skills/<dir>/` ancestor.** Manual-testing the skill-`name:` check needs a real `.../skills/<dir>/SKILL.md` path in the Write payload — a bare `mktemp` path makes the check skip entirely and return a **false PASS for every name**, even a deliberately-wrong suffix. Build the payload with `jq` against a `skills/<dir>/` path, and include a wrong-suffix case as a control: it must exit 2 to prove the validator actually engaged (otherwise an all-PASS run is meaningless).
- **Guards fail open (ADR-0001)**: parse failures, unreadable files, and unknown subcommands exit 0/1, never 2. A guard's own failure must never block the user.
- **CADENCE_BYPASS=1 exempts `list`, `configure`, `doctor`, and the session CLI actions (`declare`, `status`)** — diagnostic/CLI commands must work during maintenance; enforcement hooks are bypassed.
- **Repro scripts/fixtures containing flagged terminology must build the term by concatenation** (`TERM_W="$(printf 'white%s' 'list')"`) — the installed terminology guard blocks Writes containing the literal to any non-excluded path, including `/tmp`. CLAUDE.md and `cadence-hooks/` paths are excluded; scratch fixtures elsewhere are not.
- **A guard fix's commit message / PR body can self-block.** A `git commit -m "…"` whose message quotes the very pattern the installed guard blocks (`> .env`, a force-push example like `git push --force origin main`, a secret filename) is hard-blocked — the PreToolUse hook inspects the whole Bash command string, and your illustrative example lives inside it. Use `git commit -F <file>` (and `gh pr create --body-file`): the command then carries no guarded pattern, and file *content* isn't inspected for the redirect/secret-write check (only the Write/Edit `file_path` is). Bit me 2026-06-10 shipping the #75 redirect fix whose message contained `> .env`.
- **New shell-parsing logic that feeds the guards gets an adversarial security review before merge — TDD + CI green is not enough.** A guard-feeding parser (heredoc / substitution / quote handling in `core::shell`) can drop a command the shell *executes* — a silent **miss** (the dangerous command reaches no guard), not a false-block. Happy-path tests structurally can't find this; they only cover divergences you already thought of. Dispatch a `cadence-forge:security-reviewer` (Opus) framed as *find inputs where a dangerous command slips through unseen*: it caught a Critical heredoc evasion in 0.29.0 (#116) that 96 core tests + full CI missed. Safe invariant for any stripping transform: drop content only when the boundary is confidently located (terminator found); ambiguity → keep. "Sees less of an executed command" = miss, not fail-open — ADR-0001 protects the user from a guard *bug*, it does not license dropping commands the shell runs. **Sharpest trigger: when a predicate that previously drove only a NUDGE starts driving a STATE MUTATION** (e.g. `is_branch_switch` began gating the #70 drift baseline in 0.30.0), its false-positive tolerance *inverts* — a once-benign nudge false-positive becomes a silent guard-bypass — so re-run the adversarial review on that exact transition. The 0.30.0 self-review caught the #70 fix quietly *reopening* #70 (prose/heredoc/`git -C`/file-restore `git checkout` re-anchoring the drift baseline) this way.
- **The `markdown-lint` hook fails open when no `markdownlint` CLI is on `PATH`.** It shells out (`crates/cadence/src/markdown_lint.rs`) and *silently no-ops* if the binary is absent, so a successful `Write` to a `.md` file is **not** proof it was linted. Run `npx --yes markdownlint-cli2 <files>` yourself for evidence. The repo ships no markdownlint config, so defaults flag MD013 (line-length) / MD060 (table-padding) noise the existing docs already violate — filter to *structural* findings. (Bit the README refresh 2026-06-13.)
- **Scope env-var verification greps to shipped source.** A loose `grep -rn "CADENCE_" --include='*.rs'` over-reports the binary's live env surface — it sweeps in `tests/` and stale `.claude/worktrees/` checkouts. Grep `crates/*/src src` to see what the *shipped* binary actually honors. **`CADENCE_METRICS_DIR` is LIVE production**, not test-only — it is the *primary* resolution tier in `metrics_dir()` (`crates/metrics/src/common.rs`, ahead of the `CLAUDE_CONFIG_DIR`/`~/.claude` fallback) and is read in production by `warn_subagent_concurrency`. (A #271 red-team refuted the earlier "test-only/dead" reading of claude-configurations#120 — the shipped-source grep it prescribes was itself misread. The grep discipline stands; that one conclusion was wrong.)
- **`enforce-worktree`'s Scratch/E2E tests FALSE-ALLOW everything when the checkout sits under `.claude/worktrees/` or `/tmp`.** The Scratch harness builds fixture-repo paths from the checkout location (`CARGO_MANIFEST_DIR`-relative), so a linked worktree under `.claude/worktrees/` (or a `/tmp` checkout) makes every fixture path inherit that prefix and trip the guard's own `is_claude_managed_dir` / `is_temp_root` carve-out — every verdict becomes ALLOW, and the block-expecting tests fail on a genuinely-correct branch. **Run the suite from a carve-out-free path** (`git worktree add --detach ~/verify <sha>`). A cross-check that runs main-side from the primary checkout and branch-side from inside a linked worktree is confounded by **location, not code** — it manufactures a phantom regression. Same trap when pipe-probing the binary: `cargo build --bin cadence-hooks` first (`cargo test` does NOT build the bin → exit 127 misreads as a false ALLOW), and build fixture repos outside `/tmp` and `.claude/`. (Both bit the #226 verification, 2026-07-06.)
- **`git worktree move` leaves stale `CARGO_BIN_EXE_*` paths baked into already-compiled test binaries** — integration tests that exec the binary then fail `No such file or directory` at the *old* worktree path, and cargo sees nothing to rebuild, so the red suite reads as a phantom regression. `cargo clean` after any worktree move. (Bit the #288 merge verification after relocating a `/tmp` worktree per the carve-out rule above, 2026-07-20.)
- **The same worktree carve-out inverts `session start`'s posture tests, so a local suite can be green on a broken test and red on correct ones.** Running from a `/tmp` or `.claude/worktrees/` checkout trips `is_temp_root`, silencing the posture line: the three `posture_line_*` / `run_start_*` tests that assert posture FIRES then fail (read as "pre-existing environmental" by three separate sessions in one arc), while a test asserting overall `Allow` PASSES for the wrong reason — it controls only one contributing half of `finish()`'s join. CI runs in a primary checkout and inverts all four. **A local red/green split across posture tests is a location signal, not a verdict**; the fix for the passing-wrongly case is to pin `CADENCE_ALLOW_MAIN` via `with_worktree_env` (the pattern `posture_line_silent_when_allow_main_env_set` already establishes) or to assert on the plan-disclosure content rather than the whole verdict. (Cost 4 undetected findings across a 6-PR arc until CI ran, 2026-07-26.)
- **Test helpers that lock a process-global env var must be the ONLY helper locking it.** `persist_plan` carried its own private `ENV_LOCK` for `CADENCE_METRICS_DIR` while `registry::test_metrics_env` guarded the same global through a different mutex — two uncoordinated locks are a race no critical section can fix, and it stayed latent until added test volume shifted scheduling (surfacing first on the Windows runner as a `NotFound` unwrap on a metrics read). One global, one lock, one helper; import the existing one rather than minting a sibling. Ruling a failure like this in or out as a *production* bug turns on WHICH assertion failed, not on inspection. (cadence-hooks#446, 2026-07-26.)
- **Claude-session Bash environments can ambiently carry `CADENCE_ALLOW_MAIN=true`, which silently exempts every enforce-worktree verification.** Unit tests and pipe-probes read real process env, so a block-expecting check false-passes — and a posture-line check reads silent — with no error anywhere. Clear it explicitly (`env -u CADENCE_ALLOW_MAIN …`) or pin env inside the test (`with_worktree_env` in `crates/session/src/start.rs` is the in-tree pattern, panic-safe). Location and env are *independent* confounds: a carve-out-free checkout does not clear this one, and vice versa. (Bit two independent verification runs on #253, 2026-07-07.)
