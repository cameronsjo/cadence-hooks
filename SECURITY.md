# Security Policy

## Why this binary is hardened

`cadence-hooks` is not an ordinary CLI. It is a **security-control binary that runs
inside the agentic harness's loop** — the component that decides whether a `gh` write, a
`git push`, or an edit-on-`main` is allowed. A substituted control binary is a *silent*
compromise: a tampered `cadence-hooks` does not merely run attacker code, it **disables
the guardrails it is trusted to enforce while the agent keeps reporting green**. The
trust anchor for the whole guardrail layer is a single pinned binary, so every release is
signed and attested end-to-end and the install paths verify before they pin.

## What every release ships

Each tagged release (`vX.Y.Z`) publishes, alongside the platform archives:

| Asset | What it is |
|---|---|
| `cadence-hooks-vX.Y.Z-<platform>.tar.gz` / `.zip` | The binary, per platform |
| `checksums.txt` | SHA256 of every archive |
| `checksums.txt.cosign.bundle` | Detached keyless Cosign signature over `checksums.txt` (signature + Fulcio cert + Rekor proof) |
| `cadence-hooks-vX.Y.Z.cdx.json` | CycloneDX SBOM of the shipped binary |

Two independent attestations are generated by the release workflow:

- **Build provenance** (`actions/attest-build-provenance`) — SLSA provenance binding each
  archive to the workflow, commit, and runner that built it.
- **SBOM attestation** (`actions/attest-sbom`) — binds the CycloneDX SBOM to the archives
  it describes.

Both are stored as Sigstore bundles in the [attestations
API](https://github.com/cameronsjo/cadence-hooks/attestations) and verifiable with `gh`.

## The OIDC identity

All signatures and attestations are keyless, bound to this repository's release workflow
via GitHub's OIDC provider. A valid signature proves the artifact was produced by:

- **Identity:** `https://github.com/cameronsjo/cadence-hooks/.github/workflows/release.yml@refs/tags/vX.Y.Z`
- **Issuer:** `https://token.actions.githubusercontent.com`

Nothing else can mint a signature with that identity — not a fork, not a different
workflow, not a manual upload.

## Verifying a release

You do **not** need to trust the download path. Pick either route (or both).

### Route 1 — GitHub-native (`gh attestation verify`)

The simplest check. Requires the [`gh` CLI](https://cli.github.com/) (v2.49+).

```bash
gh attestation verify cadence-hooks-vX.Y.Z-macos-aarch64.tar.gz \
  -R cameronsjo/cadence-hooks
```

A passing run prints `✓ Verification succeeded!` and the workflow identity above. This
checks the build-provenance attestation. To additionally confirm the SBOM:

```bash
gh attestation verify cadence-hooks-vX.Y.Z-macos-aarch64.tar.gz \
  -R cameronsjo/cadence-hooks \
  --predicate-type https://cyclonedx.org/bom
```

### Route 2 — Offline / GitHub-independent (`cosign verify-blob`)

A different trust path: the detached Cosign bundle verifies against Sigstore's public
transparency log without GitHub's attestation API. Requires
[`cosign`](https://github.com/sigstore/cosign) (v2+).

```bash
# Download checksums.txt and its bundle from the release, then:
cosign verify-blob \
  --bundle checksums.txt.cosign.bundle \
  --certificate-identity-regexp 'https://github.com/cameronsjo/cadence-hooks/.github/workflows/release.yml@refs/tags/v.*' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  checksums.txt

# Then confirm your downloaded archive matches the now-trusted checksums:
sha256sum -c checksums.txt --ignore-missing
```

`cosign verify-blob` printing `Verified OK` proves `checksums.txt` was signed by this
repo's release workflow; `sha256sum -c` then chains that trust to the archive you hold.

> The `--certificate-identity-regexp` above pins the exact workflow path; a looser
> `'github.com/cameronsjo/cadence-hooks'` also works if you only need to confirm the repo.

## Reporting a vulnerability

Report security issues privately via [GitHub Security
Advisories](https://github.com/cameronsjo/cadence-hooks/security/advisories/new). For
non-security bugs, see the issue-filing guidance in the README.
